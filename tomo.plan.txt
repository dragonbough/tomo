TOMO.PLAN

tomo is a productivity tool that consists of todo lists you complete to take care of a virtual pet, called a tomo. to aid in completing these
todos, as they're called, the app features focus periods: pomodoro timers that schedule todos based on difficulty and within any given time frame.
tomo exists to make your life easier, by gamifying the tasks important to you, prospering progress and fun at the same time.

#########
timeline:
#########

phase 1: todo
- implement todo system data model into DB
- get the todo backend implementation working

phase 2: tomo (buddy)
- implement tomo system data model into DB
- get backend tomo data structure working

phase 4: pomodoro
- implement pomodoro system data model into DB

- link with qtimer feature to allow for asynchronous timings (potentially)
- fully implement focus periods feature for frontend -- takes all current todos and produces a pomodoro timer that works on each one, based on difficulty and/or time given (can be indefinite)

phase 5: polish
- iron out bugs
- make each module work more cohesively with each other

###################
how its gonna work:
###################

data.py | tomo.py | pomodoro.py | todos.py | gui.py | tests.py | main.py

data.py
- retrieves/updates todo data, tomo data and pomodoro data from DB
- retrieved data can be passed into the respective module for data structures needed

tomo.py
- models tomo behaviours using FSMs
- provides functions to manipulate tomo characteristics
- separate module that can be called by main app for tomo functionality
- tomo's bondXP slowly declines over time -- motivates you to keep completing tasks
- tomos bond level increases/drops depending on how much bondxp
- as tomos bond level increases, the tomo's sprite looks cooler and cooler
- tomo's HP declines if Bond level is kept at 0 for too long, and then it dies

pomodoro.py
- manages pomodoro timer system
- separate module called by main app for pomodoro functionality

todos.py
- receives data from data.py and uses them to fill up backend data structures
- features functions allowing for the retrieval/manipulation of in memory to dos

gui.py
- implements "views" of the data from app.py, within GUI interface in PyQt6

tests.py
- runs unit tests for each module to ensure there are no bugs

main.py
- what initialises the entire program

###########
data model:
###########

SQLITE
Todo(ID, Name, Difficulty, Completed, Points, TimeCreated, TimeCompleted, ParentID)

BASE STATS (read-only):
TomoStats(ID, BaseName, HP)
- provides base stats of tomo
TomoBondStats(TomoID, BondLevel, RequiredXP, Sprite, HP)
- provides the xp required for each bond level for a tomo, including what its sprite looks like at this level and the HP it gets
Item(ID, ItemName, Sprite, Effect)
- provides the base stats of each item you can give to tomo, which have string command effects that can boost certain stats

USER STATS (r/w):
UserTomo(ID, Name, HP, XP, BondLevel)
- table of all of the user's tomos and their current stats
UserTomoItem(TomoID, ItemID)
- table of the items the user's tomo has


PomodoroTimer(TodoID, ElapsedTime, StartTime, EndTime(?))

JSON
UserSettings(Name, Theme)


################
data structures:
################

Todos - DAG / task dependency graph
- estimated time (derived from difficulty?) -- edge weights
- id, int
- name, str
- difficulty, int
- completed, bool
- points, int

Tomos - Finite state machine
- current state, str
- transitions, dict
- action, str / custom Action type
- stats, dict

Timers - custom data type / QTimer (?)


##################
main philosophies:
##################

DBC -- each module should expect to return something and expect to receive something before doing so (post conditions and pre conditions) -- otherwise, throw errors

error checking -- ANYTIME anything is wrong in the code, make sure it crashes -- complicated systems like these can build up unseen issues which are hard to debug

user-focussed design -- make the interface easy to use and user first -- don't make it convoluted or complicated

intelligent -- the program has to be smart enough to do whatever the user is thinking it should do at all times
